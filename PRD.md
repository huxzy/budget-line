# Budget Line — Product Requirements

**Deadline: Monday 21 September 2026. Submit Saturday night.**
Hackathon: OSF × Andela invention sprint. Track: Transparency & Accountability.

---

## 1. What it is

Budget Line lets any Nigerian find out what government has budgeted for
projects where they live, by asking out loud in their own language. Every
figure it returns is shown with the page of the official budget document it
was read from, so the caller — or a journalist — can verify it independently.

This is an invention sprint proof of concept, not a production launch. It must
demonstrate the problem, the intended users, how the solution works, and why it
is worth developing further.

## 2. The user

An ordinary person on a mid-range Android phone or a laptop: a resident of Bida
who wants to know whether the clinic they were promised is funded, a journalist
checking a claim, a student. Not a civil servant, not an analyst.

Design conditions that matter: low bandwidth, multilingual access, trust and
verification, accessibility, local relevance.

## 3. The thesis

BudgIT's Tracka already makes budgets browsable for people with smartphones,
data, and English literacy. Budget Line is the **access layer** for everyone
else — voice, local language, and a verifiable citation attached to every
number. Same underlying public data, credited openly; a different audience.

## 4. Data

### 4.1 What exists today

`niger_2026_capital_projects.csv` — 1,523 capital projects extracted from the
Niger State 2026 Approved Budget (399-page PDF, published 8 January 2026).

Columns: `project, mda_code, mda_name, lga_code, lga_name, econ_code,
econ_name, func_code, func_name, amt_2024_actual, amt_2025_revised,
amt_2025_perf_jan_sep, amt_2026_approved, source_page`

**Integrity claim:** the 2026 column sums to ₦783,694,704,490.98 against the
official state total of ₦783,694,704,491.00 — a two-kobo rounding difference.
The dataset accounts for 100% of the state's capital budget. This claim is
central to the pitch and must be verifiable from the repo.

25 local government areas, plus STATE WIDE (517 rows) and OUTSIDE STATE
(1 row) buckets. 124 MDAs. 446 projects carry ₦0 for 2026.

### 4.2 Multi-state architecture (build it now, fill it later)

The product is intended to cover all 36 states and the federal tier. Structure
for that from the start, without pretending to have the data:

```
data/
  states.json              # registry of all 37 entries with status
  states/niger-2026.json   # loaded lazily, only when queried
  federal/                 # later
```

Registry shape:

```json
{
  "code": "NG-NI",
  "slug": "niger",
  "name": "Niger",
  "status": "live",
  "year": 2026,
  "projects": 1523,
  "total_2026": 783694704491,
  "document": "Niger State 2026 Approved Budget",
  "pages": 399,
  "published": "2026-01-08",
  "lgas": 25
}
```

Every other state and `federal` are `"status": "pending"` with name and code
only. The registry drives the state picker, the "not covered yet" voice
response, and the coverage story in the deck.

**One state in memory at a time.** Load a state's JSON on first request, cache
it, never load all of them.

### 4.3 Data access interface

All reads go through one module so the storage choice stays swappable:

```ts
getStates(): StateSummary[]
getState(slug): StateSummary | null
getProjects(slug, { lga?, sector?, unspentOnly?, limit?, sort? }): Project[]
getProject(slug, id): Project | null
getLgaSummary(slug, lga): { projects, total, bySector }
```

If the dataset later grows past ~50k rows (federal + multiple states), the
implementation moves to Turso/libSQL. Nothing above it changes.

### 4.4 Build-time derived fields

Generated by the conversion script, never at request time:

- `id` — stable slug, e.g. `niger-2026-p0412`
- `display` — `"₦75,000,000"`
- `plain` — `"75 million naira"` (for the UI's plain-words line)
- `spoken` — `"seventy-five million naira"` (read verbatim by TTS)
- `sector` — human sector derived from `func_code`
- `unspent_2025` — true when 2025 was approved > 0 and spend == 0

Plus indexes: by LGA, and by LGA+sector.

| 1 | First run — choose LGA, then language | Two steps; language suggestion follows the LGA |

### Out (marked PLANNED in the UI, no code)

Saved / following, re-checking across budget releases, CSV export, SMS, USSD,
toll-free number, federal tier, auth, accounts, any database, cron jobs.

**No fake phone number and no fake USSD code anywhere in the product.**

## 6. Voice behaviour

Vapi web SDK, in-browser call only. No Twilio, no phone number — Nigerian
number provisioning is slow and irrelevant to the demo.

One assistant per language, chosen before the call starts. Never swap TTS
mid-call.

### Tools (the only source of figures)

```
projects_by_lga({ state, lga, sector?, unspent_only?, limit=5 })
project_detail({ state, id })
lga_summary({ state, lga })
state_coverage({ state? })          # answers "do you have Kaduna?"
```

Each returns objects containing `spoken`, `display`, `page`, and identifiers.

### Non-negotiable agent rules

1. Never state a figure that did not come from a tool result.
2. Read the `spoken` field verbatim; never format numbers itself.
3. Empty tool result → say it is not funded in this document. Never reason
   toward an answer.
4. Never cite a page number that did not come from a tool result.
5. Cap at 5 results per turn; offer more rather than reading a list.
6. State not `live` in the registry → say so plainly and name what is covered.

### UI renders from tool results, not from speech

The client subscribes to Vapi's tool-result events and renders cards from the
structured payload. The cards are therefore always correct even if the agent
phrases something awkwardly. Never parse the agent's transcript for numbers.

The full voice script and prompt wording are a separate exercise, after the
app works.

## 7. Source verification

Pre-render capital-expenditure pages (68–101 of the PDF) to WebP at build time
with `pdftoppm`, commit the images, and overlay an absolutely-positioned
highlight box on the cited row. No pdf.js, no runtime PDF parsing.

Must include a "text only" fallback that renders the extracted row as plain
text for very poor connections.

## 8. Non-functional

- Desktop-primary (judges watch on a laptop); fully responsive down to 360px
- Light and dark, via `prefers-color-scheme`
- Tabular figures on every amount
- Works with no database and no external service except Vapi and its providers
- `npm install && npm run dev` must work from a clean clone, no setup steps
- Fallback transcriber configured so a provider blip cannot kill the demo

## 9. Judged deliverables

Working PoC, GitHub repo, demo video, pitch deck, written summary. The repo
must include the extraction script and the reconciliation check — the auditable
pipeline is part of what is being judged.

## 10. Success criteria

1. A judge asks a question by voice and gets a correct, cited answer.
2. They click the citation and see the actual budget page with the line
   highlighted.
3. Nothing on screen is invented, and nothing claimed as live is fake.
